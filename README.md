# Overview

Customer-support conversations are often short, noisy, contextual, and difficult to automate safely.

For this assignment, I selected **AmazonHelp** from the Customer Support on Twitter dataset and built an AI support agent that addresses three core problems:

1. **What is the customer asking?**
2. **How has the brand historically handled similar issues?**
3. **Should the request be automatically handled or escalated to a human?**

The system combines:

* Intent classification
* Retrieval-Augmented Generation (RAG)
* Semantic search
* Historical-resolution retrieval
* LLM-based response generation
* Risk-aware escalation
* Automated evaluation
* LLM-as-a-Judge
* Human judge calibration

The emphasis of the project is not just on building the system, but on **providing evidence that it works and understanding where it fails**.

# Problem Framing

## What Does "Good" Mean?

For this project, a good support agent should satisfy four properties:

### 1. Correct Understanding

The agent should correctly identify the customer's underlying support intent.

### 2. Grounded Responses

The generated response should be consistent with how the selected brand has historically handled similar situations.

### 3. Safe Automation

The system should not blindly automate sensitive or uncertain requests.

### 4. Measurable Performance

Each major component should have an evaluation methodology rather than relying only on subjective examples.

---

## What I Chose Not to Build

This project intentionally does **not** attempt to become a complete production customer-support platform.

It does not:

* Access live Amazon orders
* Modify customer accounts
* Process refunds
* Access private customer information
* Replace human support agents
* Automatically execute account-level actions

Instead, it focuses on **AI-assisted classification, response drafting, and escalation decisions**.

# System Architecture

The system is divided into five major components.

### 1. Data Processing

Cleans and structures the noisy Twitter support conversations.

### 2. Intent Classification

Maps incoming customer messages to one of eight operational intents.

### 3. Retrieval-Augmented Generation

Retrieves semantically similar historical AmazonHelp conversations and uses them as evidence for response generation.

### 4. Safety & Escalation

Determines whether the request can safely be automated.

### 5. Evaluation

Measures classification, escalation and response quality independently.

# RAG Pipeline

## Retrieval-Augmented Generation

A key part of the system is a **brand-specific Retrieval-Augmented Generation (RAG) pipeline**.

Instead of asking the LLM to answer purely from its pretrained knowledge, the system first retrieves relevant historical AmazonHelp conversations.

The retrieved evidence is then provided to the generator as context.

```text
Customer Message
       │
       ▼
Text Preprocessing
       │
       ▼
Query Embedding
       │
       ▼
BGE-small Embeddings
       │
       ▼
FAISS Vector Search
       │
       ▼
Relevant Historical Conversations
       │
       ▼
Context Construction
       │
       ├── Current Customer Message
       ├── Conversation Context
       ├── Predicted Intent
       └── Historical Resolutions
       │
       ▼
Mistral-7B
       │
       ▼
Grounded Support Response
```

---

## Why RAG?

A general-purpose LLM may generate a fluent response without knowing how a particular support organization historically handles an issue.

RAG provides the model with **brand-specific evidence**.

For example:

```text
Customer:
"My package says delivered but I haven't received it."

             ↓

Semantic Retrieval

             ↓

Historical AmazonHelp Cases

             ↓

Relevant Resolutions

             ↓

Mistral-7B

             ↓

Grounded Support Reply
```

This helps the generated response remain aligned with historical support behaviour.

---

## Retrieval Stack

| Component         | Technology                                          |
| ----------------- | --------------------------------------------------- |
| Embedding model   | `BAAI/bge-small-en-v1.5`                            |
| Vector database   | FAISS                                               |
| Retrieval         | Semantic similarity                                 |
| Historical source | AmazonHelp Twitter conversations                    |
| Generator         | Mistral-7B                                          |
| Context           | Current message + relevant historical conversations |

---

## Conversation-Aware Retrieval

Twitter support messages frequently depend on previous turns.

For example:

```text
Customer:
"Where is my order?"

AmazonHelp:
"Please provide the order details."

Customer:
"Still haven't got it."
```

The final message alone provides little context.

Therefore, when available, preceding conversation turns are incorporated into the retrieval and generation context.

# Intent Classification

The intent taxonomy was derived from the selected AmazonHelp support conversations.

| Intent                         | Description                                                  |
| ------------------------------ | ------------------------------------------------------------ |
| `ORDER_TRACKING_AND_STATUS`    | Order tracking, shipment status and delivery progress        |
| `LATE_OR_MISSING_DELIVERY`     | Delayed, missing or marked-delivered-but-not-received orders |
| `REFUND_AND_RETURN_STATUS`     | Returns, refunds, pickup status and refund timelines         |
| `DAMAGED_OR_WRONG_ITEM`        | Damaged, defective, incorrect or tampered products           |
| `ACCOUNT_AND_SECURITY`         | Account security and unauthorized activity                   |
| `PRIME_AND_SUBSCRIPTION`       | Prime membership and subscription-related issues             |
| `PAYMENT_AND_PROMOTIONS`       | Payments, billing, gift cards and promotions                 |
| `GENERAL_FEEDBACK_OR_CHITCHAT` | Feedback, appreciation and non-actionable conversations      |

The taxonomy is intentionally compact so that the model's decisions remain interpretable.

# Response Generation

The response-generation stage uses the retrieved historical conversations as grounding evidence.

The generator receives:

```text
Current Customer Message
+
Predicted Intent
+
Conversation Context
+
Retrieved Historical Examples
```

and produces a concise support response.

The goal is not to copy historical responses verbatim, but to use them as evidence for generating an appropriate response to the current customer.

---

# Escalation & Safety

A support agent should not automatically answer every customer request.

The escalation layer considers factors such as:

* Account-security concerns
* Unauthorized activity
* Sensitive transactional issues
* Low-confidence predictions
* Ambiguous requests
* Insufficient historical evidence
* Safety-sensitive situations

The output contains:

```text
Decision:
AUTO-HANDLE / ESCALATE

Risk:
LOW / MEDIUM / HIGH

Reason:
Explicit explanation for the decision
```

### Example

```text
Decision: ESCALATE

Reason:
The customer reports unauthorized account activity.
This requires account-level verification and should
be handled by a human support representative.
```

This makes the decision auditable rather than returning only a binary result.

# LLM-as-a-Judge

Automated evaluation was used to assess response quality.

However, an LLM judge can itself introduce bias.

Therefore, the judge was compared against human ratings.

| Metric                   |     Result |
| ------------------------ | ---------: |
| Pearson Correlation      | **0.9217** |
| Quadratic Weighted Kappa |  **0.766** |

The high Pearson correlation indicates strong agreement in overall scoring, while the QWK provides an additional measure of agreement across ordinal ratings.

This calibration provides evidence that the automated judge is reasonably aligned with human evaluation.

# Failure Analysis

## Failure Mode 1 — Ambiguous Messages

Short messages such as:

```text
"Still waiting."
```

can be difficult to classify without enough conversation context.

**Hypothesis:** better conversation-aware classification and uncertainty estimation could improve these cases.

---

## Failure Mode 2 — Novel Support Scenarios

Issues that are poorly represented in historical data can produce weak retrieval results.

**Hypothesis:** combining semantic retrieval with structured knowledge and intent filtering could improve coverage.

---

## Failure Mode 3 — Multi-Intent Requests

Example:

```text
"My order never arrived and I was charged twice."
```

A single-label taxonomy must select one primary intent even though the customer has multiple problems.

**Hypothesis:** multi-label or hierarchical intent classification would better represent such requests.

---

## Failure Mode 4 — Missing Context

An individual tweet can be impossible to interpret without previous conversation turns.

**Hypothesis:** larger conversation windows and conversation-aware retrieval could reduce these failures.

---

## Failure Mode 5 — Escalation Boundary Cases

Some issues fall between safe automation and human intervention.

**Hypothesis:** cost-sensitive threshold calibration could improve the balance between unnecessary escalation and missed escalation.

# What Is Misleading About My Headline Number?

The headline result of **93.5% intent accuracy** is strong, but it should not be interpreted as a production-readiness score.

There are several reasons.

### Small Evaluation Set

The golden set contains 200 examples and cannot represent every possible customer-support scenario.

### Brand-Specific Taxonomy

The eight intents were designed specifically for AmazonHelp.

The score therefore measures performance on this defined taxonomy rather than general customer-support understanding.

### Classification ≠ Resolution

Correctly identifying an intent does not guarantee that the generated response will correctly resolve the customer's problem.

### Retrieval Coverage

RAG depends on the availability of relevant historical examples.

Novel problems may not have sufficient supporting evidence.

### Automated Judgement

The LLM judge has been calibrated against humans, but it is still not a replacement for expert human evaluation.

### Safety

A system can have high intent accuracy while still making an unsafe escalation decision.

For this reason, classification and escalation are evaluated separately.

**The 93.5% figure should therefore be interpreted as strong performance on the defined evaluation task, not as evidence that the agent is ready for unrestricted autonomous deployment.**

# Key Engineering Decisions

### 1. Brand-Specific Agent

I selected one brand rather than attempting to build a generic support agent so that historical support behaviour could directly influence the system.

### 2. Compact Intent Taxonomy

I used eight operational intents to balance coverage and interpretability.

### 3. RAG Instead of Pure Generation

Historical support conversations are retrieved before response generation to ground the LLM in brand-specific behaviour.

### 4. Semantic Retrieval

BGE embeddings and FAISS were selected to support efficient semantic retrieval over historical conversations.

### 5. Conversation Context

Previous conversation turns are incorporated where available because isolated tweets can be highly ambiguous.

### 6. Separate Escalation Layer

Escalation is treated as a separate decision rather than allowing the response generator to independently decide whether automation is safe.

### 7. Missed Escalations

False-negative escalation cases are explicitly measured because missing a sensitive case can be more costly than unnecessary escalation.

### 8. Independent Golden Set

A dedicated hand-labelled evaluation set provides an independent benchmark for the system.

### 9. Baseline Comparison

Both a trivial and a simple ML baseline are included to quantify the value of the proposed approach.

### 10. Judge Calibration

The LLM-as-a-Judge is evaluated against human ratings rather than being treated as ground truth.

### 11. Failure Analysis

The project explicitly examines where the system fails rather than reporting only aggregate metrics.

### 12. Metric Limitations

The headline score is accompanied by an explicit discussion of what the metric does and does not demonstrate.

# Limitations

This project is an evaluation prototype rather than a production customer-support platform.

Current limitations include:

* Limited golden-set size
* Brand-specific intent taxonomy
* Dependence on historical support coverage
* No access to live Amazon account/order systems
* No real transactional execution
* No guaranteed solution for unseen support scenarios
* LLM-generated responses can still contain errors
* Automated evaluation cannot completely replace human review

The appropriate deployment model would therefore be **human-in-the-loop AI support assistance**, particularly for sensitive or ambiguous requests.

* Account compromise

# Responsible Use

The system is designed around conservative automation.

It should not:

* Ask customers to publicly disclose sensitive account information.
* Automatically resolve account-security incidents.
* Claim an action was completed when the system cannot verify it.
* Invent order, refund or account information.
* Replace human review for sensitive or ambiguous cases.

The escalation layer is specifically intended to reduce these risks.

# Final Takeaway

This project was designed around a simple principle:

> **A useful AI support agent should not only know what to say — it should know why it is saying it and when it should not say anything at all.**

The resulting system combines:

```text
Messy Customer-Support Data
          ↓
Intent Classification
          ↓
Historical Retrieval
          ↓
RAG
          ↓
Grounded Response Generation
          ↓
Safety / Escalation
          ↓
Evaluation
```

On the 200-example golden evaluation set, the system achieved:

* **93.5% Intent Accuracy**
* **0.935 Intent Macro-F1**
* **94.1% Escalation Precision**
* **78.0% Escalation Recall**
* **0.853 Escalation F1**
* **21.9% Missed-Escalation Rate**
* **4.22/5 LLM-Judge Overall Score**
* **0.9217 Pearson correlation with human ratings**
* **0.766 Quadratic Weighted Kappa**

The evaluation deliberately goes beyond a single headline metric by including baselines, judge calibration, escalation analysis, failure analysis, and limitations.
